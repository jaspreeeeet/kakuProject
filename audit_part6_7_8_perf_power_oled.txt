   Created at line ~1540 (after all setup, before task creation). ✓

7A. POWER CONSUMPTION PATTERNS
================================================================================

1. BASELINE CPU FREQUENCY:

   80 MHz (set at end of setup(), line 1532).
   Comment: "⚡ CPU idle at 80MHz (boosts to 160/240MHz for network/camera)"

2. CPU AT 240 MHz vs 80 MHz — DUTY CYCLE ANALYSIS:

   240 MHz is used for:
   - Camera capture: ~200-500 ms per capture (on-demand, feeding gesture only)
   - OTA update: Up to minutes (rare event)
   - OTA check inside NET_OLED handler: brief

   160 MHz is used for:
   - NET_SENSOR: Every 10 s, ~200-2000 ms per HTTP call
   - NET_IMAGE: On-demand, ~5-10 s per upload
   - NET_STT: Every 3 s during STT mode, ~1-5 s per upload

   80 MHz is used for:
   - All other time (idle, OLED rendering, sensor reading, audio monitoring)

   Estimated duty cycle (normal operation, no STT):
   - 80 MHz:  ~95% of time
   - 160 MHz: ~5% of time (sensor sends every 10 s + OLED polls every 2 s)
   - 240 MHz: <1% of time (camera on-demand only)

   *** During STT mode: 160 MHz jumps to ~15-20% duty cycle due to 3 s
       WAV uploads. This increases power draw significantly. ***

3. WIFI POWER MANAGEMENT — WELL OPTIMIZED:

   Line 1400: WiFi.setSleep(true)         — Light-sleep between beacons ✓
   Line 1402: WiFi.setAutoReconnect(true) — SDK-level reconnect ✓
   Line 1405: WiFi.setTxPower(WIFI_POWER_11dBm) — Reduced from 19.5 dBm ✓

   WiFi is ALWAYS ON (STA mode) — no power-off during sleep mode.
   *** SUGGESTION: During isDeviceSleeping, WiFi could be explicitly
       disconnected or put into modem sleep for further savings. Currently
       sleep mode only skips network queue dispatching but the radio
       remains associated and receiving beacons. ***
   *** However, WiFi.setSleep(true) already enables light-sleep which
       powers down the radio between beacons → ~80% WiFi power savings
       according to Espressif docs. Good enough for most use cases. ***

4. PERIPHERALS — ALWAYS ACTIVE VS ON-DEMAND:

   ALWAYS ACTIVE:
   - OLED display (I2C, always being refreshed at 10 FPS)
   - MPU6050 accelerometer (polled every 100 ms in loop)
   - PDM Microphone (I2S, continuous read in audioMonitorTask)
     *** However: mic enters 500 ms sleep polling when silent for 2 s → good. ***
   - WiFi radio (associated, light-sleep enabled)

   ON-DEMAND:
   - Camera: Only active during feeding gesture capture (~200 ms bursts)
     XCLK reduced to 10 MHz (line ~4080: "less heat, stable") ✓
   - LED (GPIO 2): Brief blinks on HTTP success (50-100 ms)
   - STT mode: Activated by 10 s left-tilt gesture, 120 s timeout

   *** ISSUE: The camera hardware (sensor + XCLK) is initialized at boot
       and stays powered even when not capturing. The XCLK line keeps
       toggling at 10 MHz, which continually powers the OV2640 image sensor.
       Consider calling esp_camera_deinit() when not in use and re-init
       on demand, though this adds ~200 ms latency. ***

7B. THERMAL CONCERNS
================================================================================

1. SUSTAINED HIGH-CPU OPERATIONS:

   a) OTA Update:
      - 240 MHz for potentially minutes
      - All other tasks suspended → reduced total load
      - Single-event, rare → NOT a thermal issue.

   b) STT Streaming Mode:
      - Audio recording + WAV construction (Core 0) + HTTP upload (Core 1)
      - 160 MHz boost every 3 seconds for upload
      - Can run for up to 120 s continuously
      *** MINOR THERMAL CONCERN: Sustained 120 s of I2S read + WAV build +
          HTTP upload uses both cores significantly. Camera is idle during
          this, mitigating somewhat. ***

   c) Normal idle operation:
      - 80 MHz, OLED render 10 FPS, sensor poll 20 Hz, audio VAD
      - LOW thermal output. The 500 ms mic sleep during silence helps.

   d) Game mode (PLAY_MENU):
      - OLED redraws every 100 ms with game logic
      - MPU6050 polled per frame for tilt control
      - No network activity during gameplay → CORE 1 mostly idle
      - LOW thermal concern.

2. CAMERA + WIFI + DISPLAY SIMULTANEOUS:

   This combination only occurs during feeding gesture:
   - Camera captures (240 MHz, ~200 ms) → Core 0
   - Image upload (160 MHz, ~5-10 s) → Core 1
   - OLED shows eating animation (100 ms frames) → Core 0

   Timeline:
   1. Camera capture at 240 MHz for ~200 ms (both cores at max)
   2. Drop to 160 MHz for HTTP upload (~5-10 s, Core 1 busy)
   3. OLED eating animation runs concurrently on Core 0

   *** MODERATE CONCERN: The WiFi SSL handshake (10-16 KB session) +
       image POST (~1-3 KB body) at 160 MHz while OLED animates is the
       highest thermal moment in normal operation. Duration is ~5-10 s.
       Mitigated by: reduced XCLK (10 MHz), QQVGA resolution (160×120),
       JPEG quality 20, single frame buffer. ***

   Summary thermal profile:
   - COOL: Normal idle + OLED + sensor polling (80 MHz, WiFi sleep)
   - WARM: Sensor + OLED poll combined HTTP calls (160 MHz, ~200 ms bursts)
   - HOT:  Camera capture + upload (240→160 MHz, 5-10 s)
   - HOT:  STT streaming mode (80-160 MHz, sustained 120 s)
   - HOTTEST: OTA update (240 MHz, minutes, but rare)

8B. ANIMATION EFFICIENCY
================================================================================

1. ANIMATION STORAGE / RENDERING:

   Animations are stored as PROGMEM const uint8_t arrays in all_pets.h.
   Each frame is a 64×32 monochrome bitmap = 256 bytes per frame.

   Rendering methods:
   a) display.drawBitmap() — Used for full-screen pet animations (50 calls).
      This is the Adafruit GFX library's optimized bitmap renderer.
      Reads directly from PROGMEM. FAST. ✓

   b) Pixel-by-pixel rendering — Used for icons (home, food, poop, sick,
      play, health, toilet, injection, clean slide). Iterates every pixel
      of the icon bitmap and calls display.drawPixel() individually.
      *** 19 drawPixel calls in the code, but they're inside nested loops. ***

      Example: drawHomeIcon() iterates HOME_ICON_WIDTH × HOME_ICON_HEIGHT
      pixels, calling drawPixel for each set pixel. For a 12×12 icon,
      that's up to 144 drawPixel calls per frame.

      *** PERFORMANCE ISSUE [MEDIUM]: Pixel-by-pixel icon rendering is
          ~10-50× slower than drawBitmap(). Icons like food, poop, sick,
          play are 24×12 = 288 iterations each. With multiple icons visible,
          this adds up. drawBitmap() would be much faster but the developer
          chose pixel-by-pixel "to prevent corruption with other animations"
          (comment at line ~1768). ***

      However, at 10 FPS on a 64×32 display, even 500 drawPixel calls
      complete well within 100 ms. Practical impact is LOW.

2. PROGMEM USAGE:

   PROGMEM is used for 6 declarations in the main .ino file:
   - sleeping_frames (2 frames × 256 bytes = 512 bytes)
   - walking_animation (6 frames × 256 bytes = 1536 bytes)
   - statusFlashBitmap (64 bytes)
   - charFrame1, charFrame2 (8 bytes each)
   - injection animation delays

   The bulk of animation data is in all_pets.h (included at line 53).
   All animation frame arrays in all_pets.h also use PROGMEM. ✓
   Confirmed by pgm_read_byte() calls throughout icon rendering code.

3. ANIMATION OPTIMIZATION OPPORTUNITIES:

   a) Walking animation skips frame 2 at runtime (line ~3065:
      "if (wFrame == 2) wFrame = 3;"). The frame data is still stored
      in flash (256 bytes wasted). MINOR — flash is abundant.

   b) playEatingAnimation() (line ~1840) and playAgeTransitionAnimation()
      (line ~3248) are blocking sequences that run multiple frames with
      vTaskDelay. These block the oledTask for their duration (1-5 s).
      Network and sensor tasks on Core 1 are unaffected.
      *** DESIGN CHOICE: Blocking animations prevent interruption, which
          is desired for cinematic sequences. ACCEPTABLE. ***

   c) Frame selection uses modulo: currentFrame % FRAME_COUNT. This is
      efficient. ✓ No unnecessary branches.

   Global String objects that are written/read across cores:

   a) currentScreenType (line 409): Written by cycleMenu() (called from
      oledTask/Core 0), read by loop() and networkTask (Core 1).
      *** THREAD SAFETY ISSUE [HIGH]: Arduino String is not thread-safe.
          String assignment involves heap allocation/deallocation. If Core 1
          reads currentScreenType while Core 0's cycleMenu() is mid-
          assignment, the heap metadata can corrupt. In practice, String
          assignment on ESP32 with short strings (<15 chars, SSO) is usually
          atomic, but NOT guaranteed. Should use a mutex or char array. ***

   b) currentEmotion (line 411): Written by syncLocalStateToUI() (called
      from multiple contexts including physiology on Core 1) AND by
      getOLEDDisplayFromServer() (Core 1). Read by displayPetAnimation()
      (Core 0).
      *** SAME ISSUE: Cross-core String read/write without synchronization. ***

   c) detectedAudioData (line 678): Protected by audioMutex. ✓ SAFE.

   d) currentMode (line 420): Dead code, never modified at runtime. SAFE.

8D. GENERAL CODE EFFICIENCY
================================================================================

1. INEFFICIENT PATTERNS:

   a) HTML page generation (wifiConfigHtmlPage, line ~1062):
      Builds a ~4-5 KB HTML string with 100+ String concatenation
      operations (page += "..."). Each concatenation may reallocate.
      *** INEFFICIENCY: Could use a fixed PROGMEM string or chunked
          response to avoid heap fragmentation. However, this only runs
          during WiFi provisioning mode (rare, one-time). LOW priority. ***

   b) Repeated MPU6050 reads:
      - checkMenuTiltGesture() reads accel data
      - checkSTTTiltGesture() reads accel data
      - detectHardwareStep() reads accel data
      - These are all called within the same 100 ms displayPetAnimation frame.
      *** MINOR INEFFICIENCY: 3 separate I2C reads per frame when one
          cached read would suffice. Each mpu.getAcceleration() is ~0.5 ms
          I2C transaction. Total: ~1.5 ms vs ~0.5 ms. LOW impact. ***

   c) isDeviceInverted() (line ~3038) calls readAllSensors() which reads
      BOTH accelerometer AND gyroscope, but only uses accel data.
      Then detectDirection() is called on the result.
      *** MINOR WASTE: gyro read (~0.5 ms) is discarded. Also, this is
          called every 50 ms from loop() for sleep detection. Could use
          a lightweight accel-only read. ***

   d) EGG_CRACK animation stored but only played once ever (first boot).
      The frame data remains in flash permanently.
      ACCEPTABLE — PROGMEM flash is not scarce.

2. RESOURCE LEAK ANALYSIS:

   a) WiFiClientSecure sslNet / sslOTA: Global objects, never freed.
      Appropriate for persistent connections in embedded context. ✓

   b) QRCodeGFX *qrcode: Allocated with new at line ~1367, never deleted.
      Leaks ~few hundred bytes. Only allocated once. MINOR.

   c) ps_malloc for capturedImageBuffer: Freed after sendImageData sends.
      Also freed inside cameraMonitorTask if new capture replaces old.
      *** CHECK: If sendImageData is never called (e.g., network down),
          the buffer persists until next capture. Not a leak per se, but
          unbounded if feeding gesture is triggered repeatedly without
          successful upload. Camera flag (cameraImageReady) prevents
          re-capture until previous is consumed. ✓ SAFE. ***

   d) STT buffers (stt_audio_buffer, stt_wav_to_send):
      Properly freed in audioMonitorTask cleanup when STT disabled. ✓
      stt_wav_to_send freed by sendSTTAudioChunk or by cleanup. ✓

   e) recording_buffer in audioMonitorTask: Allocated on speech start,
      freed on speech end or buffer full. ✓ No leak path visible.

   f) HTTPClient objects: All local to functions, .end() called before
      return on all paths. ✓

   g) wifiPrefs / petPrefs (NVS Preferences): .begin() and .end() are
      properly paired in all usage. One exception:
      *** Line ~999-1001: wifiPrefs.begin() in loop, then inside the loop
          body: wifiPrefs.end() followed by wifiPrefs.begin() for next
          iteration. This is correct but fragile — if the loop body throws
          or has an early break, wifiPrefs could be left open. MINOR. ***

3. OTHER NOTABLE PATTERNS:

   a) Base64 encoding of audio (line ~4442): Creates a potentially large
      Arduino String (32 KB base64 for 5 s recording). Passes by value
      to detectedAudioData (another String). Two copies of ~32 KB String
      on heap simultaneously.
      *** HOWEVER: This audio path appears to be dead code (sendAudioData
          is never called). The STT mode uses raw WAV upload instead. ***

   b) JSON document reuse: Global StaticJsonDocuments (g_oledDoc, g_sensorDoc)
      are reused with .clear(). ✓ Good for avoiding fragmentation.

   c) The main loop uses millis()-based tick slots for staggered scheduling:
      - Sensor every 10 s (tick % 20 == 0)
      - OLED every 2 s (tick % 4 == 0)
      This is efficient and prevents network burst overlap. ✓

   d) Daily auto-reboot (line ~3920): Reboots after 24 h uptime when
      sleeping. Good for memory fragmentation hygiene in sealed device. ✓

   e) Heap monitor (line ~3912): Reboots if free heap < 20 KB. Good
      safety net. ✓
