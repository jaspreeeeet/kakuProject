================================================================================
4A. WiFi DISCONNECT / RECONNECT HANDLING
================================================================================

[4A-1] WiFi LOSS DETECTION
--------------------------------------------------------------------------------
Location: loop() at lines 3855-3894

WiFi connectivity is checked at the TOP of every loop() iteration:

    if (WiFi.status() != WL_CONNECTED) {
        // reconnect logic
    }

This runs on Core 1 inside the Arduino loop(), approximately every 50ms
(the vTaskDelay at the bottom of loop is 50ms).

ASSESSMENT: ✅ GOOD — WiFi loss is detected promptly each loop() cycle.

[4A-2] WiFi RECONNECTION STRATEGY
--------------------------------------------------------------------------------
The reconnection logic at lines 3856-3894 follows this sequence:

1. Try most-recently-stored NVS WiFi credential (newest slot).
2. If that fails, try hardcoded WIFI_SSID / WIFI_PASSWORD fallback.
3. Each attempt has a 10-second timeout (millis()-based, non-blocking via
   vTaskDelay(300ms)).
4. If both attempts fail, the device enters "offline mode" — it just prints
   a warning and continues the loop.

FINDING [4A-2a] ⚠️ MEDIUM: ONLY TRIES ONE STORED CREDENTIAL
    The reconnect logic in loop() only tries the MOST RECENTLY stored
    credential (slot count-1). If the user has multiple saved networks,
    the older ones are never tried during reconnect.
    Compare: connectWithStoredCredentials() (used at startup only, lines 983+)
    tries ALL stored credentials newest-first, then hardcoded fallback.
    The loop() reconnect is a simplified version that skips older slots.

FINDING [4A-2b] ⚠️ MEDIUM: NO RECONNECT BACKOFF / COOLDOWN
    If WiFi is persistently disconnected, the reconnect attempt runs EVERY
    loop() iteration (every ~50ms, modulo the 10s timeout). This means the
    device will spend ~10s trying to reconnect, then immediately try again
    on the very next loop(). There is no exponential backoff for reconnect
    attempts. This wastes CPU cycles and may cause battery drain.

FINDING [4A-2c] ℹ️ LOW: NO WiFi EVENT CALLBACK
    WiFi loss is detected by polling WiFi.status(). There is no
    WiFi.onEvent() handler registered for station-mode disconnects (only
    for provisioning AP mode at line 1299). An event-based handler could
    respond faster and avoid repeated polling during connected state.

[4A-3] WiFi WATCHDOG
--------------------------------------------------------------------------------
There is NO dedicated WiFi watchdog timer. However, the firmware has:

1. Low-heap reboot (line 3912): If ESP.getFreeHeap() < 20KB → reboot.
2. Daily maintenance reboot (line 3922): After 24h uptime → reboot when
   sleeping. This incidentally "fixes" any persistent WiFi issues.

FINDING [4A-3a] ⚠️ MEDIUM: NO SERVER-UNREACHABLE WATCHDOG
    If WiFi IS connected but the server is unreachable (DNS failure, server
    down), the firmware has no specific handling. It will:
    - Continue attempting HTTP calls every 2-10 seconds (OLED poll, sensor).
    - Each call will fail with HTTP errors (timeout, -1, etc.).
    - The trackHttpResult() mechanism (lines 543-554) will increment
      httpConsecutiveErrors and call resetSSLConnection() after 3 consecutive
      failures. This resets the TLS session but does NOT back off.
    - The device will keep hammering the server at full polling rate.
    There is an isServerAlive() function (line 4526) but it is NEVER called
    from the main scheduling code — it appears to be dead code.

[4A-4] IN-FLIGHT HTTP REQUESTS DURING WiFi LOSS
--------------------------------------------------------------------------------
FINDING [4A-4a] ⚠️ MEDIUM: IN-FLIGHT REQUESTS NOT PROTECTED
    The WiFi status check is only in loop() (Core 1 Arduino loop), NOT in
    networkTask() before each HTTP call. The sequence is:
    1. loop() checks WiFi.status() OK → queues NET_SENSOR.
    2. WiFi drops.
    3. networkTask picks up NET_SENSOR, calls sendSensorDataOnly().
    4. sendSensorDataOnly() checks WiFi.status() at line 5207 → returns.

    Each individual send function (sendSensorDataOnly, sendCleanRequest,
    getOLEDDisplayFromServer, etc.) checks WiFi.status() at the top. This
    is GOOD — they will bail early if WiFi dropped between queue and execute.

    However, if WiFi drops DURING an active HTTP POST, the HTTPClient
    timeout will eventually fire (2-15 seconds depending on function), and
    the call will return a negative error code. This is handled by
    trackHttpResult().

    VERDICT: Reasonably handled. Requests will fail with timeout errors
    but http.end() is always called in the normal code path. No request
    will hang forever thanks to setTimeout values.

[4A-5] QUEUED REQUESTS WHEN WiFi DROPS
--------------------------------------------------------------------------------
The network queue (xQueueCreate(8, ...)) can hold up to 8 pending requests.
When WiFi drops:
- New requests continue being queued from loop() until checked again.
- networkTask() processes them and each function checks WiFi.status().
- Functions return early without HTTP call.
- Queue items are consumed (not re-queued on failure).

FINDING [4A-5a] ℹ️ LOW: NO RE-QUEUE ON FAILURE
    When a network request fails (WiFi down or server error), it is simply
    discarded. Sensor data, OLED poll, rewards, etc. are lost. For sensor
    data this is fine (next reading replaces it). For game rewards or
    feeding confirmations, the data is lost. However, feeding/cleaning
    effects are applied locally first, so the user doesn't notice — server
    will sync on next successful poll.

[4B-1] GLOBAL HTTP ERROR TRACKING (lines 528-554)
--------------------------------------------------------------------------------
The firmware has a clever auto-reset mechanism:
- httpConsecutiveErrors counter tracks consecutive negative HTTP codes.
- After 3 consecutive errors → resetSSLConnection() is called.
- resetSSLConnection() calls sslNet.stop(), sslNet.setInsecure(),
  sslNet.setTimeout(10), resets counter.
- trackHttpResult() is called after every HTTP call.

ASSESSMENT: ✅ GOOD self-healing mechanism.

[4B-4] BLOCKING HTTP CALLS
--------------------------------------------------------------------------------
All HTTP calls run on the networkTask (FreeRTOS task on Core 1, 16KB stack).
They are queue-driven and execute sequentially. No HTTP call runs on Core 0.

The worst-case blocking time scenarios:
- Normal API call: up to 7 seconds (2s connect + 5s read timeout)
- Image upload:    up to 15 seconds (5s connect + 10s read)
- OTA download:    up to ~135 seconds (15s connect + 120s read + stall detect)
- STT audio:       up to 25 seconds (10s connect + 15s read)

FINDING [4B-4a] ⚠️ LOW: During OTA, the network task is busy for up to
several minutes (download + flash). All other queued requests (sensor, OLED,
clean, etc.) will be blocked. This is mitigated by the OTA code suspending
other tasks anyway, but the queue will fill up (capacity 8) and subsequent
xQueueSend calls with timeout=0 will silently drop requests.

4C. TLS/SSL ROBUSTNESS
================================================================================

[4C-1] SSL CLIENT CONFIGURATION
--------------------------------------------------------------------------------
Two global WiFiClientSecure instances (lines 522-525):
- sslOTA: Dedicated to OTA firmware downloads.
- sslNet: Shared across ALL other network calls (sensor, OLED, events, image,
  audio, clean, inject, STT).

Both are configured with:
- setInsecure(): ❌ SKIPS certificate verification entirely.
- No CA certificate pinning (setCACert() never called).
- No client certificates.

FINDING [4C-1a] ⚠️ MEDIUM: setInsecure() disables TLS certificate
    verification. The device will connect to ANY server presenting ANY
    certificate, including MITM proxies. For a consumer IoT device, this
    is a security concern — someone on the same network could intercept
    all traffic including OTA firmware (code injection risk).
    MITIGATION: The OTA update does use X-OTA-Token authentication, so
    firmware replacement requires the token. But sensor data, pet state,
    and images are unprotected.

[4C-2] TLS HANDSHAKE FAILURE HANDLING
--------------------------------------------------------------------------------
- sslOTA.setHandshakeTimeout(30): Set at lines 4801, 4886.
- sslNet: NO handshake timeout set (uses default).

When TLS handshake fails:
- http.begin() returns false → function returns early (in most cases).
- getOLEDDisplayFromServer has explicit SSL reset on begin failure (line 4554).
- The trackHttpResult auto-reset (3 consecutive errors → resetSSLConnection)
  provides a general safety net.

FINDING [4C-2a] ⚠️ LOW: sslNet has no explicit handshake timeout. The
    default WiFiClientSecure handshake timeout is platform-dependent (often
    30 seconds). This could cause blocking during TLS negotiation failures.

[4C-3] TLS RETRY LOGIC
--------------------------------------------------------------------------------
- The auto-reset mechanism (resetSSLConnection at 3 errors) acts as an
  implicit TLS retry. After reset, the next HTTP call will establish a new
  TLS session.
- OTA has explicit sslOTA.stop() + reconfigure before each attempt.
- sendSTTAudioChunk() explicitly calls sslNet.stop() before each use
  (documented fix for stale TLS sessions after large POST).
- sendImageData() explicitly calls sslNet.stop() before use.

ASSESSMENT: ✅ ADEQUATE — TLS failures result in auto-reset and the next
request attempts a fresh connection. OTA handles TLS more carefully.

4D. OTA UPDATE SAFETY
================================================================================

[4D-1] OTA ERROR HANDLING (checkAndPerformOTA, lines 4775-5082)
--------------------------------------------------------------------------------
✅ COMPREHENSIVE error handling at every stage:
1. WiFi connectivity check (line 4776).
2. Version check HTTP failure → abort + clear flag.
3. JSON parse failure → abort + clear flag.
4. No update available → clean exit.
5. Download HTTP connect failure → abort + report to server.
6. Download HTTP error code → abort + report.
7. Invalid content length → abort + report.
8. Not enough flash space (Update.begin fail) → abort + resume tasks.
9. Download stall (120s no data) → break + abort.
10. Excessive read errors (150 consecutive) → break + abort.
11. Incomplete download (written != contentLength) → Update.abort() + resume.
12. Flash failure (Update.end fail) → log error + resume tasks.
13. Success → reboot.

Each failure path:
- Reports status to server via postOTAProgress("failed", ...).
- Resumes suspended tasks (audio, camera, OLED).
- Clears otaUpdateRequested flag.
- Resets CPU frequency to 80MHz.

[4D-2] OTA INTERRUPTED DOWNLOAD
--------------------------------------------------------------------------------
If download is interrupted:
- 120-second stall watchdog detects no-data condition → breaks download loop.
- Read error counter (150 tolerance with exponential backoff) handles
  transient stream errors.
- On incomplete download: Update.abort() is called → discards partial data
  from inactive OTA partition.
- ESP32 dual-partition scheme means the running firmware is NEVER modified.

FINDING [4D-2a] ✅ SAFE: Interrupted OTA cannot brick the device because
    ESP32 uses A/B partition scheme. The running partition is never touched.
    Update.abort() cleanly discards the partial write.

[4D-3] OTA ROLLBACK CAPABILITY
--------------------------------------------------------------------------------
The firmware uses ESP32's built-in dual-partition OTA:
- partitions_8mb_ota.csv exists in the project, confirming A/B layout.
- After successful Update.end(true), ESP32 marks the new partition as boot.
- ESP.restart() boots into the new firmware.

FINDING [4D-3a] ⚠️ MEDIUM: NO EXPLICIT ROLLBACK MECHANISM
    There is no code to call esp_ota_mark_app_valid_cancel_rollback() or
    esp_ota_mark_app_invalid_rollback_and_reboot(). The ESP-IDF rollback
    feature requires the new firmware to explicitly confirm it's working
    (esp_ota_mark_app_valid) or the bootloader will roll back on next reboot.
    Without explicit confirmation:
    - If CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE is set in sdkconfig, and
      the new firmware crashes before confirming → auto-rollback occurs.
    - If not configured, NO rollback protection exists.
    The firmware does call notifyServerStartupComplete() which proves
    successful boot, but it doesn't call the ESP-IDF rollback API.

FINDING [4D-3b] 🐛 BUG (from 4B-2d): OTA RETRY LOOP IS DEFEATED
    checkAndPerformOTA() sets otaUpdateRequested=false on most failure
    paths (lines 4808, 4822, 4833, etc.). The caller's retry loop at
    line 3685 checks `otaUpdateRequested` to decide whether to retry:
        for (int otaAttempt = 1; otaAttempt <= 3 && otaUpdateRequested; ...)
    Since the function clears the flag, the loop exits after 1 attempt.
    The 3-retry mechanism is essentially dead code for most failure modes.
    The only case where retry works is if checkAndPerformOTA() returns
    WITHOUT clearing the flag — which doesn't appear to happen.

FINDING [5A-2a] 🐛 HIGH: NO RUNTIME FAILURE DETECTION
    mpu.getAcceleration() and mpu.getRotation() are called WITHOUT checking

    - If MPU6050 disconnects after init → reads return garbage or zeros.
    - The raw int16_t values are divided by 16384.0 / 131.0 → could produce
      NaN or extreme values if the I2C transaction fails.

    There is ZERO runtime error detection for MPU6050 after initialization.
    No I2C error checking (Wire.endTransmission() return values are only
    checked in scanI2CDevices, not in sensor reads). No plausibility checks
    on accelerometer values. No watchdog to detect MPU6050 going offline.

    IMPACT: If MPU6050 disconnects during operation:
    - Tilt gestures will stop working (feeding, cleaning, menu navigation).
    - Step counter will read zero.
    - Game tilt controls will freeze.
    - Sensor data sent to server will be garbage.
    - But the device won't crash — it will just silently malfunction.

FINDING [5A-2b] ⚠️ MEDIUM: NO I2C BUS RECOVERY
    If the I2C bus locks up (SDA held low by a slave), there's no recovery
    mechanism. No Wire.end() / Wire.begin() cycle, no clock stretching
    recovery, no GPIO bit-banging to free the bus. The only recovery is
    a device reboot (which happens daily or on low heap).

[5E-1] NVS WRITE FAILURE HANDLING
--------------------------------------------------------------------------------
savePetState() at lines 351-366:

    petPrefs.begin("pet_state", false);
    petPrefs.putInt("hunger", g_petState.hunger);
    petPrefs.putInt("health", g_petState.health);
    // ... 10 more putInt/putUInt/putBool calls ...

FINDING [5E-1a] 🐛 HIGH: NO ERROR CHECKING ON NVS WRITES
    None of the Preferences put*() calls check return values.
    Preferences::putInt() returns size_t (bytes written, 0 on failure).
    Preferences::begin() returns bool (false on failure).
    If NVS is full or flash is worn out:
    - putInt() returns 0 → silently ignored.
    - begin() returns false → silently ignored, subsequent writes go nowhere.
    - Pet state is "saved" but actually lost → desync on reboot.

    Same issue for WiFi credential storage (saveCredentialToNVS, lines 935-948):
    - wifiPrefs.putString return values not checked.
    - wifiPrefs.putInt return value not checked.

[5E-2] NVS WRITE FREQUENCY (FLASH WEAR CONCERN)
--------------------------------------------------------------------------------
savePetState() is called from:
1. handlePhysiology() — every PHYSIO_TICK_MS (360000ms = 6 minutes)
   *** NOTE: Comment says 120 seconds but #define is 360000ms = 6 min ***
2. Feeding gesture — each time user feeds pet (~user-triggered)
3. Cleaning gesture — each time user cleans poop (~user-triggered)
4. Injection gesture — each time user gives medicine (~user-triggered)
5. Egg hatching — once at first boot
6. Low-heap reboot — once per emergency reboot
7. Daily reboot — once per 24h

CALCULATION:
- Routine writes: ~240 writes/day (every 6 minutes = 10/hour * 24)
- User actions: maybe ~20/day (feeding, cleaning, etc.)
- Total: ~260 writes/day

ESP32 NVS uses SPI flash with ~100,000 erase cycles per sector.
NVS wear leveling distributes across pages.
260 writes/day * 365 days = ~95,000 writes/year.
Each savePetState() writes 12 keys → 12 NVS entries per call.

FINDING [5E-2a] ⚠️ MEDIUM: NVS WEAR CONCERN
    ~260 save operations per day × 12 keys = ~3,120 NVS writes/day.
    Over a year: ~1.14 million key writes. ESP32's NVS has wear leveling,
    but the underlying flash has limited erase cycles. For a consumer device
    expected to last years, this write rate is borderline. The PHYSIO_TICK_MS
    interval (6 minutes) is the main contributor.

    RECOMMENDATION: Save pet state less frequently (every 30 min or only on
    significant changes) and/or before reboots. Alternatively, use a dirty
    flag to only write changed values.
