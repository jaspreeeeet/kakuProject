### ⚙️ The Processor — ESP32-S3 Dual Core

<br>

Kaku runs on the XIAO ESP32-S3 Sense — a dual-core Xtensa LX7 processor clocked at up to 240 MHz, with 512KB of internal SRAM and 8MB of PSRAM.

**Two cores. Not for marketing. For architecture.**

<br>

Core 0 handles everything time-sensitive: continuous microphone monitoring at 16 kHz, on-demand camera captures, and OLED rendering at 20 frames per second.

Core 1 handles everything network-bound: WiFi management, HTTPS requests, sensor data uploads, and the main game logic.

<br>

These are not suggestions. Tasks are pinned to specific cores using **FreeRTOS** — a real-time operating system used in medical devices, automotive systems, and industrial controllers.

Audio recording on Core 0 never stalls because Core 1 is busy uploading data. The OLED never freezes because the server is slow.

<br>

### 📡 The Network Architecture

<br>

All network communication runs through a single queue-driven task on Core 1. No function in the firmware makes direct HTTP calls.

Instead, the main loop drops one-byte request codes into a FreeRTOS queue:

<br>

```
  loop()  ──►  xQueueSend(NET_SENSOR)  ──►  networkTask  ──►  processed
  loop()  ──►  xQueueSend(NET_OLED)    ──►  networkTask  ──►  processed
  loop()  ──►  xQueueSend(NET_IMAGE)   ──►  networkTask  ──►  processed
```

<br>

This means network requests are **serialized, non-blocking, and prioritized.** The main loop never stalls waiting for a server response. Gesture detection stays responsive. Animation stays smooth.

<br>

Every request uses HTTPS with TLS 1.2, hardware-accelerated AES encryption, and connection keep-alive to minimize handshake overhead.

Two global SSL clients exist: one dedicated to firmware updates, one shared for everything else.

<br>

If three consecutive requests fail, the SSL connection auto-resets.

If ten consecutive WiFi reconnection attempts fail, Kaku switches to Access Point mode — it creates a **"KAKU_SETUP" hotspot**, serves a configuration page, and lets you enter new WiFi credentials from your phone.

No USB cable needed.

### 🧱 Memory Discipline

<br>

This is where most hobby-grade firmware fails.

And where Kaku was hardened with production-grade practices.

<br>

The ESP32 has 390KB of usable SRAM. WiFi alone consumes 40KB. Two SSL connections consume 64KB. Five task stacks consume another 54KB.

That leaves roughly **200KB** for the heap — and that heap must stay healthy for months of continuous operation.

<br>

Here's how:

<br>

**🔹 Static JSON documents.** Every repeated HTTP call reuses a pre-allocated buffer. No malloc/free cycle. No fragmentation.

**🔹 PSRAM for large buffers.** Camera frames, audio recordings, and STT chunks are stored in the 8MB PSRAM — keeping internal SRAM free for the WiFi stack and FreeRTOS kernel.

**🔹 Heap monitoring.** Every ten seconds, free heap and minimum-ever-free-heap are logged. If free heap drops below 20KB, the device saves state and reboots before a crash can occur.

**🔹 Daily maintenance reboot.** After 24 hours of uptime, during sleep mode, Kaku performs a clean restart — clearing accumulated fragmentation and resetting driver state.

### 🔐 Concurrency Hardening

<br>

Five tasks sharing data across two cores is a recipe for disaster — unless you're disciplined about it.

Kaku uses **eight mutexes**, each with a purpose-specific timeout:

<br>

| Resource | Timeout | Why |
|:---------|:-------:|:----|
| Pet state | ∞ | Critical game state, must not corrupt |
| I2C bus | 200ms | Shared by OLED + sensor — hardware can lock |
| UI strings | 20ms | Screen updates, skip-on-fail is fine |
| CPU frequency | 10ms | Register write, skip is harmless |
| Audio buffer | 100ms | Cross-core handoff |
| Camera buffer | 100ms | Cross-core handoff |
| Network data | 50ms | Sensor struct copy |
| STT data | 50–100ms | WAV chunk handoff |

<br>

No infinite waits on hardware. No unprotected shared state. No "it works on my desk" concurrency.

<br>

The CPU frequency itself is mutex-guarded. Both cores adjust clock speed dynamically — **80 MHz at idle, 160 MHz for HTTP, 240 MHz for camera and OTA.**

Without a lock, simultaneous writes to the frequency register would produce undefined behavior. With the lock, it's deterministic.

Kaku supports full OTA firmware updates. Press a button on the web dashboard, and the device:

<br>

**1.** Checks the server for a newer firmware version

**2.** Downloads the binary over HTTPS with three-attempt retry logic

**3.** Suspends all non-essential tasks to maximize download reliability

**4.** Writes to a secondary flash partition (A/B partitioning)

**5.** Reboots into the new firmware

**6.** If the new firmware fails, the bootloader rolls back automatically

<br>

You never open the case. You never connect a cable.

Kaku updates itself — safely, with rollback protection, while showing a live progress bar on its face.

**Every Kaku ever shipped can receive new features, personality tweaks, animation packs, and stability improvements forever.**

### 🛡️ Stability Hardening Was Not An Afterthought.

<br>

We conducted a formal reliability audit of the entire firmware.

The result: **seven critical issues, ten high-severity issues, nineteen medium and low-severity issues** — all identified, categorized, and resolved before this campaign launched.

<br>

Specific hardening measures:

<br>

**🔹 I2C bus protection.** Every sensor and display access is mutex-guarded with 200ms timeouts. If the I2C bus locks (a known failure mode of the MPU6050), the system recovers within 200ms instead of hanging forever.

**🔹 SSL connection auto-recovery.** After three consecutive HTTP failures, the TLS session is torn down and rebuilt. No manual intervention. No stuck states.

**🔹 Heap exhaustion guard.** Free memory is monitored every ten seconds. Below 20KB triggers an automatic state-safe reboot before the WiFi stack can crash.

**🔹 Response size validation.** Every server response is size-checked before being read into memory. A malformed or oversized response is discarded, not allocated.

**🔹 NVS state persistence.** Pet state is saved to flash before every reboot — scheduled, emergency, or OTA. Your Kaku never loses its memories.

<br>

### 🔒 Privacy: Camera and Microphone

<br>

Kaku has a camera and a microphone. We take this seriously.

<br>

**📷 Camera** — Captures a single JPEG frame only when you trigger a feeding gesture (deliberate three-second tilt). It does not stream. It does not record video. It does not activate without physical input.

**🎙️ Microphone** — Two modes. Passive voice activity detection runs locally — audio energy is measured on-device, and silence is never transmitted. Active speech-to-text requires a deliberate ten-second tilt gesture to activate, and automatically deactivates after two minutes of silence.

**🚫 No wake word.** There is no always-listening mode. Kaku cannot be voice-activated.

**🔐 Encryption.** All data is transmitted over HTTPS with TLS 1.2 encryption. No plaintext. No unencrypted endpoints.

**📄 Open documentation.** We are committed to publishing the camera and microphone activation logic so you can verify exactly when and how these sensors operate.

<br>

**You control when Kaku sees. You control when Kaku listens. Full stop.**

<br>

---

<br>

### 🚚 Hardware Delays

<br>

Global component supply chains remain unpredictable.

The ESP32-S3, MPU6050, and SSD1306 are all widely available commodity components — not custom silicon — which reduces sourcing risk significantly.

<br>

**Mitigation:**

✦ Two alternate suppliers identified for every critical component

✦ Enclosure uses standard injection molding with single-cavity mold (faster, cheaper iteration)

✦ One-month buffer built in between production and shipping

<br>

If delays occur, we will communicate them immediately with specific revised dates — **not vague "we're working on it" updates.**

<br>

---

<br>

### 🐛 Firmware Complexity

<br>

6,300 lines of real-time multi-core firmware is not trivial.

Bugs will exist. Edge cases will surface when hundreds of devices run in hundreds of different WiFi environments.

<br>

**Mitigation:**

✦ Firmware has undergone two formal audits (pre-hardening and post-hardening) with documented findings

✦ OTA updates mean every shipped device is patchable within minutes of a fix

✦ Daily maintenance reboot ensures slow-burn issues self-heal every 24 hours

✦ Detailed serial logging can be activated remotely for diagnostics

<br>

**We don't promise zero bugs. We promise fast fixes, delivered over the air, to every device simultaneously.**

<br>

---

<br>

### ☁️ Server Dependency

<br>

Kaku connects to a cloud server for food recognition, speech-to-text, state sync, and OTA updates.

If that server goes down, some features are temporarily unavailable.

<br>

> **📐 Design Note — Color Guide**
> - **Overall feel:** Premium but approachable. Engineered but warm.
> - **Rhythm:** Light → warm → DARK (engineering) → light → white → DARK (proof) → gray → light → DARK (closing)
> - **The dark sections are intentional contrast breaks.** They signal "now we're being serious" and make the return to light feel like relief and optimism.
> - **Purple accent is the thread.** Every CTA button, every highlight, every link uses #6C5CE7. It's the brand color that ties everything together without ever appearing in the background.
> - **Emoji usage:** Section banners only + inline feature markers. Never in body text. Never more than one per line.
