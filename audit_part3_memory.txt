A2. LEAK VECTORS — REPEATED ALLOC WITHOUT FREE
───────────────────────────────────────────────

 FINDING A2-1: capturedImageBuffer — REPEATED ALLOC/FREE CYCLE (LOW RISK)
   Location: L4184 (cameraMonitorTask), freed at L4182 (before re-alloc) and L5329 (sendImageData)
   Pattern: Every feeding gesture allocates a new buffer, copies from camera fb, then sendImageData
   copies again to binary_data and frees the original. Both paths free correctly.
   Risk: If the image is captured (L4184) but sendImageData is never called (e.g. WiFi disconnects
   permanently), capturedImageBuffer will remain allocated until the next capture overwrites it.
   This is NOT a growing leak — bounded to one buffer at a time (max ~60KB in PSRAM).
   VERDICT: Acceptable. Single allocation cap.

 FINDING A2-2: recording_buffer — REPEATED ALLOC/FREE IN AUDIO TASK (LOW RISK)
   Location: L4380 (audioMonitorTask), freed at L4446
   Pattern: Speech detected → alloc ~160KB in PSRAM → record → base64 encode → free.
   The alloc/free cycle happens per speech event. After free, recording_buffer is set to NULL (L4447).
   Risk: If speech detection starts but the recording loop never hits the stop condition
   (silence timeout or buffer full), recording_buffer stays allocated. However, both conditions
   are guaranteed to fire eventually (SILENCE_TIMEOUT=2000ms, buffer-full check exists).
   **CONCERN**: base64::encode(recording_buffer, recorded_bytes) at L4432 creates a temporary
   Arduino String (detectedAudioData) that can be ~213KB for a 160KB recording. This is allocated
   from internal heap (not PSRAM), potentially fragmenting internal RAM. The String lives until
   the next speech event overwrites it. See C3 for more detail.
   VERDICT: Functionally safe, but fragmentation concern.

 FINDING A2-3: stt_audio_buffer + wav_buf — STT STREAMING CYCLE (LOW RISK)
   See section A4 below for full lifecycle analysis.

A4. stt_audio_buffer AND stt_wav_to_send LIFECYCLE
───────────────────────────────────────────────────

 Declaration:
   L752: uint8_t *stt_audio_buffer = NULL;   (global, initialized to NULL) ✅
   L764: uint8_t *stt_wav_to_send = NULL;    (global, initialized to NULL) ✅
   L766: SemaphoreHandle_t sttDataMutex = NULL;

 ALLOCATION (stt_audio_buffer):
   L4245: Allocated in audioMonitorTask when sttModeActive && first read.
   Size: STT_MAX_AUDIO_SIZE = 128KB (PSRAM via ps_malloc).
   NULL check: L4246 — if alloc fails, sttModeActive set to false, continues. ✅

 FREEING (stt_audio_buffer):
   L4317: Freed when sttModeActive becomes false (cleanup block at L4314-4328).
   Set to NULL at L4318. ✅
   **POTENTIAL ISSUE**: The cleanup block at L4314 is inside the `if (sttModeActive)` block,
   after the `continue` statement at L4335. The code checks `if (!sttModeActive)` at L4314
   WITHIN the `if (sttModeActive)` block. This means the check at L4314 fires when sttModeActive
   was true at the top of the loop iteration but was changed to false by another core (volatile)
   between the outer check and the inner check. This is a valid race-condition cleanup pattern.
   However, if sttModeActive is set to false by another core AFTER the `if (sttModeActive)` check
   at L4235 fails and the code falls through to the normal VAD path, then this cleanup block
   is NEVER REACHED. The buffer would remain allocated until sttModeActive is set to true again
   (which re-enters the block and the next disable triggers cleanup).

   RACE WINDOW: sttModeActive=true → Core1 sets it false → audioTask loop iteration
   starts, checks sttModeActive at L4235 → false → skips entire STT block → falls to
   normal VAD. Cleanup never runs.

   **LEAK SCENARIO**: stt_audio_buffer (128KB PSRAM) remains allocated indefinitely if
   STT mode is disabled by Core 1 right as the audio task loop wraps around.
   SEVERITY: MEDIUM — 128KB PSRAM leak until next STT activation or device reboot.
   The daily reboot (L3921) and low-heap reboot (L3912) mitigate this.

 ALLOCATION (stt_wav_to_send):
   L4292: Ownership transferred from wav_buf. wav_buf is allocated at L4284.
   Protected by sttDataMutex. Previous stt_wav_to_send freed at L4291 before overwrite. ✅

 FREEING (stt_wav_to_send):
   Path 1: L4325 — cleanup when STT disabled (same cleanup block as stt_audio_buffer).
   Path 2: L5923-5925 — sendSTTAudioChunk() takes ownership, NULLs the pointer.
   Path 3: L5931 — sendSTTAudioChunk() frees wav_data if size < 100.
   Path 4: L5951 — sendSTTAudioChunk() frees wav_data after HTTP POST.
   All paths set pointer to NULL. ✅

   Same RACE WINDOW as stt_audio_buffer applies — if STT disabled at exactly the wrong
   moment, stt_wav_to_send may not be freed by the audio task. However, sendSTTAudioChunk()
   will still pick it up from the queue and free it (L5951). Still safe for this pointer.

 VERDICT: stt_audio_buffer has a narrow race-condition leak window (MEDIUM risk).
          stt_wav_to_send is properly managed across all paths.

C1. REPEATED DIFFERENT-SIZE ALLOC/FREE IN PSRAM
────────────────────────────────────────────────

 FINDING C1-1: capturedImageBuffer (PSRAM) — VARIABLE SIZE
   Allocated at L4184 with fb->len which varies per camera capture (JPEG compression
   yields different sizes per frame). Old buffer freed at L4182 before new alloc.
   Pattern: free(old) → ps_malloc(new_size) → copy → later free in sendImageData.
   FRAGMENTATION RISK: MEDIUM over days. Each capture can produce a different-size JPEG
   (10-60KB depending on scene complexity). Over thousands of captures, PSRAM heap
   develops fragmentation. Mitigated by daily reboot (L3921).
   RECOMMENDATION: Use a fixed-size buffer (e.g., max JPEG size from camera config).

 FINDING C1-2: stt_audio_buffer (PSRAM) — FIXED SIZE ✅
   Always STT_MAX_AUDIO_SIZE (128KB). Allocated once per STT session, freed on disable.
   No fragmentation concern from this buffer itself.

 FINDING C1-3: wav_buf (PSRAM) — VARIABLE SIZE
   Allocated at L4284 with wav_total (= stt_audio_size + 44). stt_audio_size varies
   based on how much audio was captured in the 3s window. Could be 2KB to 128KB.
   Ownership transferred to stt_wav_to_send → freed in sendSTTAudioChunk (L5951).
   FRAGMENTATION RISK: MEDIUM during active STT sessions. Multiple different-size WAV
   buffers allocated and freed every 3 seconds.
   RECOMMENDATION: Pre-allocate a fixed WAV buffer alongside stt_audio_buffer.

 FINDING C1-4: recording_buffer (PSRAM) — FIXED SIZE ✅
   Always MAX_RECORDING_SIZE + WAV_HEADER_SIZE = 160044 bytes. No fragmentation concern.

 FINDING C1-5: binary_data (internal malloc) — VARIABLE SIZE
   Allocated at L5322 with capturedImageLength (varies per JPEG). This uses internal
   heap (malloc, not ps_malloc). Freed at L5362 or L5405.
   FRAGMENTATION RISK: HIGH for internal RAM. Variable-size allocations from the
   limited ~390KB internal heap. Camera images can be 10-60KB.
   RECOMMENDATION: Use ps_malloc for binary_data since it's just a copy for HTTP POST.

C3. STRING CONCATENATION IN LOOPS (ARDUINO String FRAGMENTATION)
────────────────────────────────────────────────────────────────

 FINDING C3-1: wifiConfigHtmlPage() — MASSIVE String concatenation (L1062-1220)
   ~50+ `page += "..."` concatenations building an HTML page.
   Each concatenation may reallocate the String's internal buffer, creating
   fragmented heap allocations. Final page is likely 4-8KB of HTML.
   RISK: MEDIUM. But this function is only called during WiFi provisioning (AP mode),
   not during normal operation. Once WiFi is configured, this code path is not re-entered.
   RECOMMENDATION: Use F() macro for string literals / reserve() the String upfront.

 FINDING C3-2: base64::encode in audioMonitorTask (L4432)
   Creates a String from 160KB recording. The resulting ~213KB String is stored in
   global `detectedAudioData` (L678) which is an Arduino String. When overwritten
   on next speech event, the old 213KB is freed and a new one allocated.
   RISK: HIGH fragmentation of internal heap. 213KB is more than half of the ESP32's
   internal RAM (~390KB total). This may not even succeed on internal heap.
   MITIGATING FACTOR: This uses Arduino String which may internally use PSRAM on
   ESP32-S3 with PSRAM-enabled builds (depends on menuconfig/board settings).

 FINDING C3-3: base64::encode in captureImageBase64() (L5186)
   Creates a String from camera fb. The function appears unused (comment at L5199 says
   "Audio recording is now handled by audioMonitorTask"). This is likely dead code.
   If called, it creates a potentially large String on the stack frame of whatever calls it.

 FINDING C3-4: String payload in sendAudioData() (L5434-5436)
   `String payload = "{\"audio_data\":\""  + audioBase64 + "\"}"`
   If audioBase64 is 213KB, payload is ~213KB+20B. Multiple intermediate String
   objects are created during concatenation.
   RISK: HIGH. Two copies of ~213KB data exist momentarily during concatenation.
   RECOMMENDATION: Use chunked transfer or send raw binary instead of base64-in-JSON.

 FINDING C3-5: String payload serialization from JSON docs
   Multiple locations (L2471, L4759, L5117, L5277, L5522, L5792) use:
     `String payload; serializeJson(doc, payload);`
   These are typically small (<1KB). Low fragmentation risk.

 FINDING C3-6: WiFi SSID key construction in loops (L914, L931-938, L992-995)
   `String key_s = "wifi" + String(i) + "_s";` inside for-loops iterating max ~5 times.
   Creates small temporary Strings. Negligible risk.

E2. LOW-MEMORY DETECTION AND RECOVERY
──────────────────────────────────────

 FINDING E2-1: Critical heap reboot (L3912-3916)
   ```
   if (freeHeap < 20000) {
     Serial.println("🚨 CRITICAL: Heap below 20KB — rebooting to recover!");
     savePetState();
     delay(500);
     ESP.restart();
   }
   ```
   Threshold: 20KB free internal heap → save state → reboot.
   GOOD: This is a solid last-resort recovery mechanism. ✅
   CONCERN: Only monitors internal heap. If PSRAM is exhausted but internal heap
   is fine, this won't trigger. PSRAM exhaustion causes ps_malloc failures which
   are handled individually (e.g., L4246 disables STT).

 FINDING E2-2: Daily maintenance reboot (L3921-3926)
   ```
   static const unsigned long DAILY_REBOOT_MS = 86400000UL; // 24 hours
   if (millis() > DAILY_REBOOT_MS && isDeviceSleeping) {
     savePetState();
     ESP.restart();
   }
   ```
   GOOD: Prevents long-term fragmentation accumulation. Only reboots when device
   is sleeping (minimal disruption). ✅
   CONCERN: Uses millis() which overflows at ~49.7 days. After overflow, the condition
   `millis() > DAILY_REBOOT_MS` becomes false and the safety reboot stops working.
   The device would run indefinitely without maintenance reboots.
   RECOMMENDATION: Track uptime separately or use modular arithmetic.

 FINDING E2-3: Individual allocation failure handling
   - L4246: stt_audio_buffer alloc fail → disable STT mode ✅
   - L4188: capturedImageBuffer alloc fail → just prints error, doesn't retry ✅
